# moy_sh — the terminal's shell

The C shell of `docs/os_2026-11/system.md` §1: POSIX `sh` syntax over
the kernel's processes and the store, derived from dash (`UPSTREAM.md`). How a
session runs — the push-model input, the fork as an arena snapshot, the exec as
a host spawn, the built-ins — is `moy_sh.h`'s header.

## Tasks

A session runs on the task that feeds it; the running session is that task's
(`moy_sh_g` is thread-local), so the SSH face's session on its own task
(`native/moy_ssh`) runs beside the Terminal's. Whatever touches the files
tree or crosses the door goes through the host table's `hop`
(`moy_sh_hop`), which on that face runs it on the console's task. The
Terminal's and the serial face's lines run on their session's runner
(`moy_sh_board.h`): a task of its own, in strict turn with the console's,
whose `hop` hands the turn back for the crossing and whose waits park the
run while the console's frames go on.

## Questions

A command asks the user nothing over its stdin on an interactive face: it
asks the session a QUESTION (`moy_sh_ask`, `moy_sh.h`). The question takes
the prompt's place and ends the run; the next line typed is its answer, and
the line that asked runs again, its answers handed back in the order they
were typed (`moy_sh_answer`) until a run of it asks nothing more. A re-run
shows nothing of what it writes to the terminal until it takes its last
answer, since the run before showed it, so a transcript holds each line once;
when the question is over the host's `unask` tells the door (`unask JOB`),
and what a role command kept for the line's runs goes (`pkg`'s checked
download, which the re-runs take up in place of fetching it again). The door's
first run of a command nobody consented to asks so (`runtime/shell/sh_door.py`),
and so do `pkg`'s licence, password and install questions
(`runtime/shell/sh_roles.py`). A SECRET question (`MOY_SH_ASK_SECRET`, the
console's password) is answered unseen: the Terminal's face draws a `*` a
character, the stream face (`native/moy_tty`) echoes nothing, Enter echoes the
prompt alone, neither keeps the line in its history or completes it, and the
session zeroes its answers when the line is done with them. A face whose
commands read a stream with no terminal (`ssh host pkg ...`) turns questions
off (`moy_sh_set_questions`), and the command reads its answers from stdin.

## Memory

A session takes its record and its arena from the host's `alloc` (PSRAM on a
board, `heap_caps` with the default heap only where there is no PSRAM); a pipe's buffer, a file's chunk and a fork's snapshot are taken
while a run needs them and returned after. A built-in's working memory (a
walk's names, `sort`'s blocks, a text tool's line) is a process block
(`moy_sh_palloc`), which its process frees if a signal, an error or `exit`
ends it before the built-in can; a block's END (`moy_sh_pend`) lets go what
it holds outside the session as it goes, so a network command's socket and
its hold on the radio (the `sh` tag, `native/moy_kernel/moy_lease.h`, which
a Zero's own station takes no row for) go on every way out. A network command keeps no buffer of its own: `ping`'s
figures and the times of its last eight echoes are on its stack. A pipeline's stages run one after
another, so a pipe holds its writer's whole stream: 1 MB in memory, 4 KB on
a board without PSRAM (the C3 Zero), and past that in a temporary file of the
store (`/etc/pipes/*.tmp`, the store's `system/pipes`) written and read a
chunk at a time, so a pipe's memory stays at one chunk on each side of the
file. The file and its folder go at the pipe's last close, whatever ended it
(the writer killed, the session closed or taken over), and a boot's first
spill sweeps what a reset left. A stream the store has no room for, or past
4 MB in the file (`MOY_SH_SPILL_MAX`, so `yes | head` ends), ends its writer
with one line, `pipe: no room to hold N KB`, and the reader reads what came
before it. Where there is no PSRAM a shell's block also leaves
`MOY_SH_HEAP_RESERVE` (16 KB, `moy_sh_board.h`) of the heap free: the SSH
server's packets and the network's buffers come from the same heap, and
Dropbear ends a session whose allocation fails ("m_malloc failed"). A
command past the reserve fails where it ran ("Cannot fork", `pipe: out of memory at N KB`). The screen face takes its record,
its session and its grid the same way at its first open (`moy_sh_screen_new`)
and gives them back at `close`. The serial face's session lives from its first
`sh` line to the boot's end, except across a run that stops the VM
(`native/moy_play/moy_play_stop.c`): an idle one is freed with the VM, so it
cannot split the block the compiled module loads into, and made again in its
folder after the run (`moy_sh_board_release`, `moy_sh_board_restore`), its
variables a new session's. The objects hold one writable word, thread-local,
`moy_sh_g` (the running session's state, and between runs the serial face's,
parked there so the board keeps no root of its own): `tests/test_moy_sh.py`
compiles them as a board does and fails on any other `.data` or `.bss`. The Terminal's face takes its record (the line, the history, the candidates and the log's row buffers) the same way at `moy_sh_face_new` and gives it back at `moy_sh_face_free`; a frame allocates nothing but the log's row buffers when the grid grows. The recovery floor's screen takes its record, its UI context, its shape and its pixels the same way at `moy_sh_floor_new`. A text app takes its front, its record and its screen (`moy_sh_app_open`), and the editor its text a block at a time, from the same `alloc` while it is open. A face's runner takes its record from `alloc`, and at its session's first run a task whose 24 KB stack is PSRAM (`MOY_SH_RUN_STACK`, the SSH face's task's), 12 KB of internal SRAM on a board without PSRAM, and two semaphores; all go at `moy_sh_board_runner_end`, before the session is freed, the task deleted as it was made (`moy_task_delete`). A session's arena (`MOY_SH_ARENA`, the serial face's and a job's) is 128 KB, and 12 KB on a board without PSRAM, the SSH face's there. The kernel's loop keeps the parked runs' jobs in four slots of its own (`moy_loop_job`).

## The suite

`tests/test_moy_sh.py` builds `host/sh_main.c` under AddressSanitizer and
UBSan and runs every script in `tests/moy_sh/` — one per feature and one per C
built-in — against the transcript beside it (`MOYBYTE_UPDATE_GOLDENS=1`
rewrites them). The harness's stand-in OS is listed in its header.
`tests/moy_sh/serial/` does the same for the serial face: each line fed as
the `sh` word feeds it, with the VM stopped or (a `vm_` script) a stand-in
console behind the door. Every serial and suite script replays through the
screen face too, and its grid's lines must be the serial face's output.
An `app_` script drives a text app over the serial face and replays
through no other face, since the screen face draws the app on a screen of
its own. `host/app_main.c` runs a text app on an app heap that refuses
any request over a cap, and `test_the_editor_asks_for_no_text_bigger_than_a_block`
opens, grows, undoes and saves files many blocks long in `edit` and `vi`
under a cap of one block, and yanks and deletes them whole in vi's VISUAL.
`tests/test_moy_term.py` holds the grid's escapes, `tests/test_terminal.py`
the Terminal app and its text apps over the host binding (vi's selection
in reverse video among them), `tests/test_recovery_floor.py` the editor on
the floor.
